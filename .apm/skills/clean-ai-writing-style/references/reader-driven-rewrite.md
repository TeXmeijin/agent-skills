# Reader-Driven Rewrite(対象読者ドリブンの全面改稿)

README、導入ガイド、LP、案内文など「特定の読者に判断させる文書」を改稿するときに読む。記事の部分磨きではなく、文書全体の価値の立て直しが必要な場面を扱う。批評の道具(監査スクリプト、二系統批評)は SKILL.md 本体の手順をそのまま使い、この参照はその上流と運用を決める。

## 1. 読者と判断を定義する

本文に触れる前に、次の2文を書く。

- この文書を読むのは誰か(例: README = 初見のエンジニア)
- その人は読んで何を判断・実行したいか(例: 「自分はこれを入れるべきか」を判断し、10分で初回実行に到達する)

この2文が以後すべての判断の目的関数になる。表現の好みではなく「読者の判断が進むか」で採否を決める。

完了条件: 2文が書けており、既存本文のどのセクションがどちらにも貢献していないかを言える。

## 2. 構造から直す

表面の言い換えで勝負しない。よくある構造欠陥:

- 書き手(所有者)の関心事が冒頭に来ている。設計思想や内部事情は、読者の判断材料(何をしてくれるか→実物の見本→使い始め方)の後ろか、既存セクション内の数行に畳む。
- 英語文書の定型を直訳した見出し(「What this is」→「これは何か」)。日本語文書の慣習(導入は見出しなし、または「概要」)に置き換える。
- 機能として約束したものに手順・参照先がない行き止まり。
- 同じ命題を複数セクションで繰り返す重複。

言い換えを何度直しても改善が頭打ちになるなら、それは構造問題のシグナルとして、セクションの削除・統合・移動を先に行う。

完了条件: 各セクションが手順1の判断にどう貢献するかを1文で言える。

## 3. 語彙は実在検証で選ぶ

- 対応表(「adjudication→裁定」のような固定訳)を執筆者に渡さない。対応表の語自体が未検証だと、実在しない訳語が全文へ一括で入り、執筆者は指示に従っただけなので検出もされない。
- 渡すのは手順にする: 疑わしい語をすべて列挙 → 1語ずつ「日本の技術記事(Zenn・Qiita・企業テックブログ)で実際に使われている言い方か」をWeb検索で確認 → 実在する言い方に置換。
- 選んだ結果は置換表(旧語 / 新語 / 実在根拠)として報告させる。据え置いた語にも理由を書かせる。
- CLI名・設定キー・ディレクトリ名と連動する語は、文章だけ変えると実装と食い違う。据え置くか実装ごと変えるかを明示的に判断する。

完了条件: 置換表があり、各行に実在根拠がある。

## 4. 執筆と批評を別コンテキストで行う

書いた本人は自分の文章を疑えない。役割ごとにコンテキストを分ける。

- 執筆、独立レビュー、語彙検証は、会話履歴を引き継がない新しいセッションまたはサブエージェントで行う。
- 同一ペイン・同一セッションを使い回す場合は、コンテキストのクリアが完了したことを確認してから次の指示を送る。実際に起きた事故: クリア指示が実行中ターンの後ろに並んで順序が逆転する、長文の貼り付けが未送信のまま止まる。指示後に「新しいコンテキストで、意図したタスクが開始したか」を画面で確認する。
- 二系統批評(Structure / Expression)は SKILL.md 本体の手順を使う。構造の指摘と表現の指摘を混ぜない。

完了条件: 執筆者と批評者が別コンテキストであること、批評開始時に批評者のコンテキストが新規であることを確認した。

## 5. 事実は現物で裏取りしてから書く

「◯◯の手順は docs にある」「このフラグで比較できる」のような参照・断言は、書く前に参照先とコードの現物を確認する。批評者にも、本文とコードの突き合わせを審査基準として渡す。

完了条件: 本文中の参照・断言に、現物未確認のものがない。
