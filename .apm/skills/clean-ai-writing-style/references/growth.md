# Growth

この skill は、実際の指摘から得た失敗パターンを溜めて使う。ただしその知識は、指摘を受けた文書の固有名、実物の文言、社内やプロダクトの内部名を含むまま書かないと検出力が落ちる。抽象化して同梱すると、語を替えても元の文脈が読み取れる状態が残る。そこで知識だけを実行環境側へ置き、skill 本体には手順だけを置く。

## 知識ストア

置き場所は `$XDG_DATA_HOME/clean-ai-writing-style/`。`XDG_DATA_HOME` が未設定なら `~/.local/share/clean-ai-writing-style/` を使う。

| ファイル | 役割 | いつ読むか |
|---|---|---|
| `failure-patterns.md` | 一般化済みの失敗パターン。判断に使う本体 | レビュー開始時に必ず |
| `growth-log.md` | 未一般化の生の指摘を預かるキュー | 追記時と蒸留時だけ |

ストアが無い環境では、批評ループと監査スクリプトだけで進める。パターンの蓄積を始めるなら、上記ディレクトリを作り、次の見出しだけを持つ2ファイルを置く。

```bash
STORE="${XDG_DATA_HOME:-$HOME/.local/share}/clean-ai-writing-style"
mkdir -p "$STORE"
printf '# Failure Patterns\n\n## 目次\n\n---\n' > "$STORE/failure-patterns.md"
printf '# Growth Log\n\n蒸留待ちのキュー。追記専用。\n' > "$STORE/growth-log.md"
```

ストアの中身を skill ディレクトリへコピーしない。skill を共有・公開する経路に、そのまま乗ってしまう。

## 追記する範囲

セッション中に、AIが自力で修正できず、指示者が具体的に指摘したものを `growth-log.md` へ追記する。対象は **出力された文章そのものを読めば検出できる失敗** に限る。自分の再読、評価シナリオ、subagent の自己申告では追記しない。

| 指摘の性質 | 書く先 |
|---|---|
| 段落順、セクション分割、見出し、語の選択、読者知識の渡し方、文書の読者設計 | `growth-log.md` |
| 調査計画の立て方、仮説の優先順位、外部事例の採否 | 調査・意思決定を扱う指示先 |
| 検証せず断定した、前言を撤回した、不可逆操作の確認を怠った | 認識規律を扱う指示先 |
| ルールをどのレイヤーへ置くかの判断 | 再発防止の配置を扱う指示先 |

判定に迷う場合の問い: その指摘は、出力された文章そのものを読めば検出できるか。文章を読んでも分からず、作業の進め方を見ないと分からないなら範囲外。範囲外は書く先だけを提示し、追記はしない。

### 追記形式

```md
## YYYY-MM-DD - 短い名前

- Trigger: 指示者が何を問題視したか
- Bad output: 実際の悪い表現
- Why it failed: なぜ失敗か
- Detection: 次回どう検知するか
- Replacement principle: 次回どう直すか
```

## 蒸留

キューが8件を超えたとき、または蒸留を依頼されたときに、レビュー作業とは切り離して実行する。

本体は読むたびに全文が判断材料になる。増えれば増えるほど1件あたりの効き目が薄れるので、成功条件は「パターンが増えたこと」ではなく「同じ分量で検出できる失敗が増えたこと」にある。

### 1. キューを分類する

各エントリを3つに分ける。

- **統合**: 既存パターンの Bad / Detection を強めれば表現できる。既存項目へ追記し、新規見出しは作らない。同じ失敗が別の場面で出たものは、ほぼこれに該当する。
- **新規**: 既存のどのパターンでも検出できない失敗。新しい見出しを立てる。
- **範囲外**: 文章そのものを読んでも検出できない失敗。上の表に従って書く先を提示し、本体へは入れない。

完了条件: 各エントリについて、どの既存パターン名へ統合するか、なぜ新規なのか、どこへ回すのかを言える。

### 2. 一般化して書き換える

エントリの Trigger は特定のセッションの記録なので本体へは持ち込まない。持ち込むのは、次回の文章に対して当てられる検査だけ。

- Bad には、その失敗が起きた実際の文言を残す。ストアは実行環境の中なので、固有名や実物の文言を薄めない。薄めると同じ失敗を次回検出できない。
- Detection は検索語か、本文へ当てる問いにする。「気をつける」で終わるものは検査になっていない。
- Replacement は、代わりに書く文の例まで置く。

完了条件: 書いた項目を単独で読み、元のセッションを知らない読者が同じ失敗を検出できる。

### 3. 本体の重複を落とす

蒸留を反映したあと、`failure-patterns.md` を通しで読み、次を処理する。

- Detection の検索語が重なる項目を探す。同じ検索語で見つかる失敗が複数の見出しに分かれている場合、1項目へまとめて系統別の箇条書きにする。
- 一方が他方の特殊例になっている項目を探す。特殊例側に固有の検出方法があるなら残し、無ければ一般側へ吸収する。
- 目次のグループと各項目の中身がずれていないか確認する。ずれていたらグループを移す。

完了条件: 同じ検索語を持つ見出しが2つ以上ない。目次が本文の順序と一致している。

### 4. キューを空にする

反映したエントリと、範囲外として回したエントリを `growth-log.md` から削除する。

完了条件: `growth-log.md` に未処理エントリが残っていない。

### 報告

- 統合したエントリと、統合先のパターン名
- 新規に立てたパターン名と、既存で検出できなかった理由
- 範囲外として回したエントリと、回した先
- 本体で統合・削除した項目と、その根拠
