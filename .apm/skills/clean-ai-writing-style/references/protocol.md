# Relentless Protocol

`SKILL.md` の relentless loop を、依頼タイプ別にどこまで適用するか決めるための参照。

## Scope By Request

固定手順は常に判断順序として使う。ただし、ユーザー依頼の範囲を超えて成果物を広げない。

| 依頼タイプ | 必ず行うこと | 省略・縮約すること |
|---|---|---|
| 編集まで求められた | loop 全体を通す。必要なら見出し、段落順、表、例、締めを変える。修正後に再読ゲートを通す。 | なし。 |
| レビューだけ求められた | loop の批評まで通し、書き換え軸まで出す。構造欠陥が多く、軸だけでは直し方が伝わらない場合は短い書き換え案も出す。 | 完全文の書き換え案は、ユーザーが求めた場合、または「必要なら」と言われていて構造欠陥が複数ある場合だけ出す。書き換え案を出さない場合、再読ゲートは「直すなら見る観点」の短い列挙に留める。 |
| 見出しだけ求められた | 前後1セクションを読み、本文の実際の仕事と前後接続から見出しを評価する。Structure critic は必須。Expression critic は見出し語、曖昧さ、本文とのズレに限定する。 | 知識台帳と段落タスクは、見出し判断に必要な最小要約に縮約する。本文の書き換え案は出さない。本文表現の網羅指摘は、見出し判断の根拠になる場合だけ触れる。 |
| チャット内本文だけ渡された | 一時ファイルを作らず、監査カテゴリを手動で全件確認する。前後セクションが無い場合、知識台帳の「既に持っている知識」は対象本文から推定した前提として明示する。 | 行番号、ローカル監査コマンド、前後セクションの実読は要求しない。 |

対象ファイルがローカルにある場合、監査範囲は原則として対象セクションの開始行から終了行にする。前後セクションは接続確認のために読むが、依頼範囲でない限り監査対象へ含めない。

## Audit Categories

`scripts/audit_text.py` は次のカテゴリを出す。ヒットは自動的な誤りではないが、すべて正当化する。

- `否定・逆接`
- `曖昧動詞`
- `AI抽象名詞`
- `評価語`
- `擬人法`
- `会話由来の唐突さ`
- `見出しリスク`

## Knowledge Ledger

本文を直す前に、この5項目を埋める。

| 種別 | 内容 |
|---|---|
| 読者が既に持っている知識 | 直前までに本文上で説明済みの知識 |
| このセクションで渡す前提知識 | 評価や結論の前に必要な知識 |
| このセクションで新しく教える知識 | セクションの主題 |
| 具体例として使う材料 | 例、実務経験、コード、エラー文 |
| 入れない知識 | 今入れると飛躍・脱線になる知識 |

## Flow Check

フローチャート、状態遷移、設計図、読者状態、論点ノードがある場合は、本文を書く前後で照合する。

| ノード | 本文段落 | 判定 |
|---|---|---|
| 前提ノード | 該当段落 | 先に提示されているか |
| 根拠ノード | 該当段落 | 評価より前にあるか |
| 評価ノード | 該当段落 | 根拠を受けているか |
| 結論ノード | 該当段落 | セクション全体を回収しているか |

評価語を先に出す場合は、読者にとって地図になる抽象度に留める。`妥当`、`理想的ではない`、`優先度は高くない`、`自然`、`素直`、`ずれる`、`成立している` のような判定語は、根拠ノードを本文上で渡した後に置く。先出しするなら「何を検討するか」という問いの形にする。

フローチャート上で論点の種類が分かれた場合は、同一セクション内の順序調整で解決しようとしない。特に「Aを導入する意義」と「Aの実装詳細・親クラス・命名・変更優先度の評価」のように、読者状態の目的が違うノード列は、別セクションに分ける候補にする。

## Rewrite Rules

禁止:

- 見出しを維持するために本文を広げる。
- 会話で出た具体例を、抽象化せず日記のように置く。
- 表にすべきでない論理展開を表に押し込む。
- 読者が持っていない誤解を勝手に想定して否定文を書く。

修正後のセクションは、セクションの仕事を本文だけで果たしている必要がある。

## Reread Gate

編集まで求められた場合、対象セクションだけでなく前後1セクションを再読する。各ゲートに対して「通過」または「未通過なので追加修正した」を記録する。

| ゲート | 判定 |
|---|---|
| 接続 | 前セクションから唐突に話題が変わっていない |
| 知識 | 読者が知らない概念を評価・結論に使っていない |
| 段落 | 各段落の役割が1つに絞られている |
| 設計図 | フローチャートがある場合、ノード順と本文順が対応している |
| 見出し | 本文の実際の仕事から見出しが決まっている |
| 例 | 具体例が主張を助けており、日記化していない |
| 表 | 比較・分類・対応関係だけを表にしている |
| 表現 | 曖昧動詞、擬人法、空虚な締め、不要な否定文を処理した |

## Output

レビューだけを求められた場合:

1. セクションの仕事
2. 知識台帳
3. 問題点
4. 書き換え軸
5. 必要なら書き換え案

編集まで求められた場合:

1. 何を変えたか
2. 全体再読ゲートの結果
3. 知識ストアへ追記した指摘の有無(範囲外として別の指示先へ回したものがあれば、それも書く)

長文にしすぎない。網羅的な作文ではなく、文章の欠陥を決定的に見つけて直す。
