# Clean AI Writing Style

AI生成の日本語文章を、読者知識、セクションの仕事、段落タスク、表現癖の順に追い詰める skill。局所的な言い換えで満足せず、根拠を残して構造から直す。

## Load

開始時に必要な参照だけ読む。

- 常に読む: 知識ストアの `failure-patterns.md`。場所は `$XDG_DATA_HOME/clean-ai-writing-style/`(未設定なら `~/.local/share/clean-ai-writing-style/`)。既知の失敗パターンが目次付きで入っている。
- 本文の表現や整形を直すときに読む: `japanese-tech-writing` skill。表現と整形の正本はこちらにあり、`failure-patterns.md` と競合したらこちらを取る。記事など読み物として読ませたい文章では `cognitive-rhythm-writing` skill も併用する。
- 依頼タイプ別の範囲、ゲート、出力形式が必要になったら読む: `references/protocol.md`
- 記事全体の構成設計、既存記事の大幅改善、新規記事の初稿前すり合わせでは読む: `references/reader-state-flow.md`
- README・導入ガイドなど、特定読者の判断を助ける文書の全面改稿では読む: `references/reader-driven-rewrite.md`(読者と判断の定義、構造からの立て直し、語彙の実在検証、執筆と批評のコンテキスト分離)
- 指摘を記録するとき、蒸留するとき、ストアがまだ無いときに読む: `references/growth.md`

失敗パターンは、指摘を受けた文書の固有名や実物の文言を含んだまま書かないと検出力が落ちるため、skill には同梱せず実行環境側に置いている。ストアが無い環境では、この Loop と監査スクリプトだけで進めてよい。作り方は `references/growth.md` にある。

完了条件: ストアがある場合、既知の失敗パターンを今回のレビュー観点に入れている。

## 批評ループ

### 1. 対象範囲を確定する

対象ファイルまたは対象文章を特定する。ファイルなら対象セクションと前後1セクションを読む。チャット内本文だけなら、前後セクションなしで判断する。

完了条件:

- 対象セクションの開始行と終了行が分かっている。
- 直前セクションが渡した知識を1〜3点で言える。
- 直後セクションへ渡すべき知識を1〜3点で言える。

### 2. 監査を先に走らせる

ローカルファイルなら対象範囲に監査をかける。

```bash
# 本 skill のディレクトリで実行する
python3 scripts/audit_text.py <file> --start <line> --end <line>
```

チャット内本文だけなら、一時ファイルを作らず同じ観点を手動で確認する。

完了条件: 監査ヒット、または手動確認した監査カテゴリを記録し、各ヒットが問題か許容かを判断している。

### 3. セクションの仕事を1文で定義する

見出しや既存本文に引っ張られず、前後接続を含めて、そのセクションが読者をどこからどこへ進めるかを書く。

完了条件: セクションの仕事が、前後セクションとの接続を含む1文になっている。

### 4. 知識台帳を作る

本文を直す前に、読者が既に持っている知識、先に渡す前提知識、このセクションで新しく教える知識、具体例として使う材料、入れない知識を分ける。

完了条件: 以後のレビューや本文に、台帳にない新概念を突然出していない。

### 5. 段落タスクを設計する

各段落の役割を先に並べる。1段落に1タスクだけ置く。

完了条件: 各段落について「この段落を読むと読者の何が進むか」を言える。

### 6. 設計図へ照合する

ユーザーがフローチャート、状態遷移、設計図、読者状態、論点ノードを提示している場合は必ず照合する。提示がなくても構成が崩れているセクションでは簡易フローチャートを作る。

記事全体の構成設計、既存記事の大幅改善、新規記事の初稿前すり合わせでは、本文より先に Reader State Transition Flow を作る。これは検査器ではなく、読者の事前状態、各セクションで渡す知識、事後状態を人間とすり合わせる上流設計図である。具体的な書き方は `references/reader-state-flow.md` に従う。

完了条件:

- 前提、根拠、評価、結論の順序が本文段落と対応している。
- 評価語が、必要な前提・根拠より前に出ていない。
- 目的の違うノード列を、同一セクション内の順序調整だけで処理していない。
- 1〜2ノードしか満たしていない説明を、複数段落で過剰に実装していない。
- 記事全体や大幅改善では、本文を書き始める前に Mermaid flowchart を提示し、人間が構成レビューできる状態にしている。

### 7. 二系統で批評する

本文を直す前に Structure critic と Expression critic を分けて通す。サブエージェントが使える環境では同時に投げる。使えない環境では同じ会話内で2回に分け、混ぜて考えない。

- Structure critic: 前後接続、セクションの仕事、知識台帳、段落順、見出し、表や箇条書きの要否。
- Expression critic: 曖昧動詞、擬人法、不要な否定、会話由来の唐突さ、空虚な締め、AIっぽい決め台詞。

完了条件: 2系統の指摘を別々に記録し、採用する指摘と採用しない指摘を決めている。

### 8. 依頼範囲に合わせて返す、または直す

レビューだけなら、書き換え軸まで出す。編集まで求められたら、見出し、段落順、表、例、締めを含めて必要な範囲で直す。見出しだけなら本文を書き換えない。

依頼タイプ別の範囲、全体再読ゲート、出力形式は `references/protocol.md` に従う。

完了条件: 成果物がユーザー依頼の範囲を超えず、Step 3 の仕事を満たしている。

## Growth

この skill を読んだセッション中に、AIが自力で修正できず、指示者が具体的に指摘したものは、知識ストアの `growth-log.md` へ追記する。追記対象は、**出力された文章そのものを読めば検出できる失敗**に限る。構成、段落順、見出し、語の選択、読者知識の渡し方、読者設計が該当する。

文章を読んでも分からず、作業の進め方を見ないと分からない失敗(調査計画の立て方、検証せず断定したこと、ルールの配置先判断)は、この skill の守備範囲ではない。ここへ書くと、次回以降のレビュー全体が本来と違う方向へ引っ張られる。書く先だけを提示して、追記はしない。

キューが8件を超えたとき、または蒸留を依頼されたときは、レビュー作業とは切り離して `failure-patterns.md` へ統合し、キューを空にする。同時に本体側の重複も落とす。項目を増やすこと自体は改善ではなく、同じ分量でより多くの失敗を検出できる状態が目標になる。

判定表、追記形式、蒸留手順は `references/growth.md` に従う。

完了条件: 追記対象がある場合、範囲内であることを判定した上で、具体的失敗を検知可能な形で記録している。
