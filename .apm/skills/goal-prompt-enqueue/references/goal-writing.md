# GOALファイルの書き方（記憶ゼロの自律実行エージェント向け）

このファイルは `SKILL.md` の Step 3〜5 から参照される詳細手順。`goal-template-generator` skill の Pre-GOAL Fact Pass / Decision Funnel / Uncertainty Handling / Template Shape を、「実行者は本文以外の記憶を一切持たない」「実行中に質問できる相手がいない」という制約に合わせて再構成したもの。

## Pre-GOAL Fact Pass

GOAL・CONTEXT・CONSTRAINTS・DONE WHEN・VERIFYを書く前に、雰囲気や推測で書かない。安価に取得できる事実は先に集める。並列に読める場合は並列に読む。

集めるべき事実:

- 依頼文が参照したファイル・コードシンボル・設定・テスト・ドキュメント・issue/PR本文・diff・ローカルメモ
- 現在のブランチ・リポジトリ状態・package scripts・テストコマンド・CI定義・環境名
- 許可済み/環境が既に公開している読み取り専用のクラウド・運用系事実（`aws ... describe/get/list`、ログクエリ、デプロイメタデータ等）
- バージョン依存の挙動が絡む場合の公式ドキュメント最新版
- `AGENTS.md` / `CLAUDE.md` / `README` / 既存skillの指示などのプロジェクトルール

事実として素早く取得できるものを「不明点」に数えない。取得してから書く。悪い例:

- 「対象のAWSリソースが分からない」→ 認可済みの読み取り専用AWS CLIで一覧できるなら、それは不明点ではない
- 「現在の実装が分からない」→ ファイルパス・シンボルが検索できるなら不明点ではない
- 「検証コマンドが分からない」→ package scripts・CI定義・READMEで分かるなら不明点ではない

認証情報がない・ネットワークがない・sandbox制約・権限不足で取得できない場合のみ、その旨と試した方法を明記して `BLOCKED FACTS` に回す（`UNCERTAINTIES` には入れない）。

## なぜ「事前の認識合わせ」がgoal-template-generatorより重い比重を持つか

`goal-template-generator` は対話の続きとして使われるため、生成後に実行者が疑問を持てば「その場でユーザーに聞く」という逃げ道がある。

このSKILLが生成するGOALファイルは違う。配置後、数時間〜半日後に記憶ゼロの実行者が拾い上げて完全に無人で走らせる。実行者が判断に迷っても、その場に質問できる相手がいない。つまり:

- 「実行者に確認してもらう」という前提のUNCERTAINTIESは実質的に機能しない（実行者は止まるか、当てずっぽうで進めるかの二択になる）。
- 後戻りしにくい判断（製品・UX方針、スコープの境界、マージ先ブランチ、承認が要る操作の線引きなど）は、配置前にSKILL呼び出し元との間で解決しておく必要がある。
- 実行中に本当に解決不能な分岐（未知の実行時状態に依存する等）は、UNCERTAINTIESではなく `STOP RULES` として「その状況になったら安全側に倒して止まる」という具体的な指示に変換する。

したがって、このSKILLが生成する最終的なGOALファイルの `UNCERTAINTIES` は、ほぼ常に「None」になるべきである。何かがUNCERTAINTIESに残っているなら、それは配置前の認識合わせが不足しているサインとして扱う。

## Decision Funnel（発動するとき）

依頼が製品挙動・UX方針・ゲームルール・コピーのトーン・作業範囲の境界・受け入れ基準をまだ固めている最中のときに使う。5ステップ:

1. 関連する現状の実装・ドキュメントを先に読む。「参照元ファイル・現在の挙動・既存の制約」を名指しできる状態にしてから質問する。
2. 大きな質問リストを一度に投げず、GOAL・制約・受け入れ基準を変えうる論点だけを一問一答的に確認する。
3. 会話中に決定台帳をつける。各論点を次のバケットに分類する。
4. GOALを書く前に台帳を読み返し、矛盾がないか確認する。
5. 台帳から書く。直近発言だけを根拠にしない。

決定台帳のバケット:

- `CONFIRMED DECISIONS`: 承認済み・一次資料で裏付けられた決定 → CONTEXT/CONSTRAINTS/DONE WHEN/VERIFYへ
- `LIKELY DECISIONS`: 方向性は固まっているが正式確定ではない → DEFAULT DECISIONSへ（理由付き）
- `AUTONOMOUS IMPROVEMENT AREAS`: 実行者に自律的に反復してほしい領域（スクリーンショット確認→修正のループ等） → PLAN/VERIFYの具体的なイテレーションループへ
- `OPEN DECISIONS`: 安全なデフォルトが無く本当に未解決 → 後述「実行不可能な残留論点の扱い」へ
- `OUT OF SCOPE`: 魅力的だが意図的に対象外 → CONSTRAINTS/STOP RULESへ

## 実行不可能な残留論点の扱い

Decision Funnelを経ても`OPEN DECISIONS`が残る場合、このSKILLでは選択肢は2つしかない（実行者に聞く、という3つ目の逃げ道が存在しないため）:

1. **配置前にSKILL呼び出し元へ確認する**（0〜10問ゲートの追加ラウンドとして）。後戻りしにくい・製品方針を左右する論点は基本的にこちら。
2. **STOP RULESに変換する**。「その分岐に遭遇したら、実装を進めず状況を記録して停止する」という具体的な安全策として書く。技術的な実行時分岐（例: 全候補が非現実的なレイテンシになる、等）はこちらが適切なことが多い。

`UNCERTAINTIES`セクションに「実行者の確認が必要」という体裁の項目を残したまま配置しない。

## Template Shape

```md
# GOAL Template: <task name>

## 最初に読む（任意、本文が長い場合のみ）
<最初に読むべきファイル・状況サマリを箇条書き。中規模以上のタスクで有効。>

## CONFIRMED FACTS
- <事実> — <出典（ファイルパス:行番号、PR番号、コマンド実行結果、依頼者本人の発言、等）>

## BLOCKED FACTS
- <取得したかったが出来なかった事実> — <試した方法と、取得できなかった理由>

## DEFAULT DECISIONS
- <実行者が確認なしに採用してよい決定> — <安全・可逆・根拠がある理由>

## GOAL
<一つの明確で測定可能なミッション。無関係な複数の成果を束ねない。>

## CONTEXT
<関連リポジトリ・ファイル・issue/PR/ログ・依頼者の意図・現状・既存の決定。不明点は明記。>

## DECISION LEDGER
Decision Funnelを使った場合のみ含める。

- Confirmed decisions: <確定事項、または「上記CONFIRMED FACTS以外になし」>
- Likely decisions: <方向性のみ確定、または「なし」>
- Autonomous improvement areas: <実行者が自律的に反復すべき領域、または「なし」>
- Out of scope: <対象外、または「なし」>

## UNCERTAINTIES
- None. 残る不明点はBLOCKED FACTS・DEFAULT DECISIONS・STOP RULESのいずれかに分類済み。
（本当にUNCERTAINTIESが残る場合、それは配置前に解決すべきサイン。詳細は「実行不可能な残留論点の扱い」参照。）

## CONSTRAINTS
- <変えてはいけないもの、保つべきパターン、機微データの扱い、スコープ境界>
- <実行体制: 実装作業（コード編集・大量ファイル読み込み・並列調査）は経済ティアのモデルのサブエージェントに委譲し、実行者自身（その時点で利用可能な最上位モデル）は計画・危険操作の可否判断・最終レビュー・ドキュメント更新に専念すること。サブエージェントのモデルは実行プラットフォームに合わせて指定する（Claudeで実行する場合はサブエージェント= Sonnet を明示指定、Codexで実行する場合は相応の経済ティア）。並列化できる独立した単位が複数ある場合はサブエージェントを並列実行してよい。>

## PRIORITY
1. <最優先。通常は安全性・正確性・依頼者の意図>
2. <次点。通常は最小スコープ・保守性>
3. <あれば良い程度。スコープを広げてまで追わない>

## PLAN
1. <まず状況を確認・検証する>
2. <（該当する場合）Decision Funnelの決定台帳を消化する>
3. <狭い範囲の実装作業。サブエージェント委譲を明記する>
4. <台帳がAutonomous improvement areasに割り当てた反復ループを実行する>
5. <検証する>
6. <報告を残す（このセッションの記憶は残らないため、コミットメッセージ・PR追記・OUTPUT本文が唯一の記録になる旨を明記）>

## DONE WHEN
- <観測可能な最終状態>
- <スコープ内の既知の回帰が残っていない>

## VERIFY
- <コマンド・手動確認・ログ・スクリーンショット・レビュー手順>
- <検証できなかった場合、何が検証できず、なぜかを明記する>

## OUTPUT
- <最終報告に含めるべき内容>

## STOP RULES
- <どんな状況になったら、進める前に停止するか。実行不可能な残留論点はここに具体化する>
```

## 実行方法の明記（必須）

生成するGOALファイル本文には、以下の趣旨を必ず含める（文言は調整してよいが `/goal` という文字列は必ず残す）:

> このMarkdown本文全体を、`/goal` ネイティブコマンドが使える環境ではそれに渡して実行すること。`/goal` が無い環境では、本文をそのままGOALとして扱い、以下の指示に従うこと。

これは実行者側のランナー実装が `/goal` 機能の有無を検出する既存の運用に対応するための必須マーカー。省略しない。
