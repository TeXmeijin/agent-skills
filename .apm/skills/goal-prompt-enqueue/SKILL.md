# Goal Prompt Enqueue

気合を入れた高品質GOALプロンプトを、後で高性能モデルにまとめて実行させるために貯めておく——このフローの「貯める側」。依頼を、あとで完全に無人で実行される自己完結GOALファイルに変換し、キューへ積む。取り出して1件ずつ実行するのは対になる `goal-prompt-dispatch`。

## このSKILLが前提にしていること

生成したファイルは、配置後しばらくして（数時間〜半日後）記憶ゼロの実行者が拾い上げ、`workspace_directory` にcdして本文をそのままGOALとして実行する。実行中、実行者は誰にも質問できない。

この制約が、通常のGOALテンプレート生成と比べて2点重くなる:

1. **配置前の疑問潰しが実行の成否を決める。** 実行者が途中で判断に迷っても後戻りできない。後戻りしにくい・製品方針を左右する論点は、ファイルを書く前にこのSKILLの呼び出し元と決着させる。
2. **実行体制を本文に明記する必要がある。** 実行者（その時点で利用可能な最高性能モデル、以下「メイン」）が全部自分で実装すると、コンテキストとトークンを浪費し長時間実行の枠を無駄にする。調査・並列読み込み・個別実装は経済ティアのモデルを割り当てたサブエージェントに委譲し、メインは最上位モデルのまま計画・危険操作の可否判断・最終レビューに専念する体制を、生成するGOALファイル自身に指示として書き込む。生成したGOALはClaude / Codexどちらが拾うか不明なので、サブエージェントのモデルはプラットフォームごとに具体的に指定する（Claudeで実行するならサブエージェント= Sonnet 必須、Codexで実行するなら相応の経済ティア。どちらもメインは最上位モデル）。

## 全体の流れ

```
0. 事前の認識合わせ(0〜10問、必要なら) → 1. Pre-GOAL Fact Pass → 2. (該当する場合)Decision Funnel
→ 3. GOALファイル執筆 → 4. キューの inbox/ へ配置
```

Step 1〜3の詳細手順（Pre-GOAL Fact Pass、Decision Funnel、Template Shape、Uncertainty Handling）は `references/goal-writing.md` にまとめてある。書き始める前に読むこと。このSKILL.md本体は全体の流れと、このSKILL固有の要件（配置・実行体制・`/goal`マーカー）に絞る。

## Step 0: 配置前の認識合わせ（0〜10問）

高性能モデルの自律判断に任せるのが基本スタンスであり、依頼のたびに大量の質問をするのは本末転倒。ただし「決めの問題」（一度配置すると後戻りしにくい・実行者が創作で埋めると危険な判断）は先に固めておいたほうが安全。

**質問すべきサイン**（1つでも該当すれば、その論点だけ聞く。全部まとめて聞く必要はない）:

- 製品・UX方針、ゲームルール、コピーのトーンなど「何が正解か」が依頼者の頭の中にしかない判断が残っている。
- 対象PRのマージ先・作業ブランチ・既存worktreeの使い回し可否など、間違えると実行者が独断で不可逆な選択をしてしまう境界がある。
- 依頼文だけでは「機能面」「範囲」「対象外」の輪郭が2通り以上に解釈できる。
- 承認が要る操作（本番、課金、外部公開、削除、破壊的git操作）の許可範囲が依頼文から読み取れない。
- 実行体制（サブエージェント委譲の粒度、並列化してよい単位）について依頼者が明示的な意向を持っていそうだが、まだ言っていない。

**質問しなくてよいサイン**（Fact Passで埋まる、または実行者の裁量に委ねてよい）:

- コードを読めば分かる実装詳細（関数名、ファイル配置、既存パターンの踏襲）。
- 既存のSSOT/計画書/AGENTS.md/CLAUDE.mdに答えがある。
- 依頼者が既に明言している範囲内の細部（DEFAULT DECISIONSとして処理できる）。

質問は0件でもよい（既存の詳細な計画書がある技術移行タスク等）。逆に、上限の目安は10問程度。それを超えて聞きたくなる場合、依頼そのものがまだGOAL化できる段階に達していない可能性が高い（先にDecision Funnelで論点を整理する、または依頼者と会話で詰める）。

質問して得た回答は、そのままDecision Funnelの決定台帳（`CONFIRMED DECISIONS`）に反映する。

## Step 1〜3: 事実収集・Decision Funnel・執筆

`references/goal-writing.md` を読み、その手順に従う。特に次の2点はこのSKILL固有の必須要件なので省略しない:

- **実行体制の明記**: CONSTRAINTSに「実装作業は経済ティアのモデルのサブエージェントに委譲し、メイン（実行者自身）は最上位モデルのまま計画・危険操作の可否判断・レビューに専念する」という趣旨を必ず入れる。サブエージェントのモデルはプラットフォーム別に具体指定する（Claude実行なら Sonnet 必須、Codex実行なら相応の経済ティア）。一方でメイン側は固有名で決め打ちしない（「その時点の最上位モデル」と書く。特定の期間限定モデル名を焼き込むと数ヶ月で陳腐化するため）。
- **`/goal` マーカー**: 本文中に文字列 `/goal` を含む実行方法の一文を必ず入れる（`references/goal-writing.md` の該当節に文言例あり）。

## Step 4: 配置

生成したGOALファイルは、ホーム直下のキューに書く:

```
~/.goal-prompt-queue/inbox/<slug>.md
```

キューを skill ディレクトリ配下ではなくホーム直下に置くのは、enqueue と dispatch を Claude / Codex どちらから呼んでも同じ実体を指すようにするため。skill 配下（`~/.claude/skills/...` や `~/.codex/skills/...`）だと、呼び出した agent によって別のディレクトリになり、片方で積んだGOALをもう片方のランナーが取りこぼす。

- `<slug>`: 内容が分かる短い英数字スラッグ。同日に複数件ある場合や日付順が処理順に影響する運用なら `YYYYMMDD-<slug>.md` の形にする。
- frontmatterは次の3項目のみ:
  ```yaml
  ---
  title: <短い題名>
  workspace_directory: <絶対パス。実行者がcdして作業を開始する場所>
  created_at: <YYYY-MM-DD>
  ---
  ```
  `completed_at` / `result` 等の実行後フィールドはランナー側が完了時に追記するものなので、生成時点では書かない。

### 4フォルダ運用について（このSKILLの責務外・前提の共有のみ）

このSKILLは `inbox/` への配置までを担当する。取り出して実行する側は対になる `goal-prompt-dispatch` skill が担い、競合を避けるため `inbox → inprogress → done / error` の4フォルダで動く。ランナーのセットアップ（定時トリガー登録）自体はどちらのSKILLの範囲外だが、次の前提とGOALファイルの内容が矛盾しないようにする:

- ファイルは実行開始時に `inprogress/` へ移動され、成功時は `done/`、失敗時は `error/` へ移動される想定。GOALファイル本文に「doneフォルダに自分で移動する」といった、この前提と矛盾する指示を書かない。
- `~/.goal-prompt-queue/` 配下に `inbox/inprogress/done/error` が無ければ、初回配置時に作成してよい（無くても`inbox/`さえあれば配置自体は成立する）。

### 別ツールから覗きたい場合

キューの実体は `~/.goal-prompt-queue/` 配下で完結する。ノートアプリやファイラ等から一覧・編集したい場合は、任意の場所からこのディレクトリへ symlink を張ればよい（skill 側はその symlink の有無に依存しない）。

### 注意: キューはバージョン管理に含めない

`~/.goal-prompt-queue/` 配下は実行キューであり、個別タスクの内容（PR番号・社内文脈を含みうる）が入る。skill のソースとは別物なので、dotfiles リポジトリや skill 公開リポジトリにコミットしない。
